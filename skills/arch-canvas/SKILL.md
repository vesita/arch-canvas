# 架构画布（arch-canvas）

用户侧栏有一个「架构画布」面板，你和用户**在看同一张图**。用户拖图形，你读文本。

## 0. 这是一张共享画布 —— 放开手改，但改动要小、要说清

**没有「AI 只读」闸门了**，`arch_write` / `arch_edit` 随时可用。安全性由**检查点**兜底：
每一次落盘都留一份快照（标明是 AI 改的还是用户改的），用户能在面板顶栏「历史」里一键退回。
所以你不需要先征求许可才能动手，但也别把检查点当成一次大改的许可证：

- **能改一处就别重画整张。** 用户手动摆的布局是他的劳动成果，`arch_write` 只用于初稿与结构性重画；
- **改动越小，用户越容易看懂你做了什么** —— 说明里点名节点 id（画布上会短暂高亮）；
- **拿不准用户要不要你改时，先问一句**，或者把结构写在回复里（需要时贴一小段 mermaid）。
  这不是权限问题，是协作问题。
- **改坏了不用慌**：告诉用户「刚才那步可以在『历史』里退回 #编号」，别自己闷着反复覆盖。

如果项目里还没有图库（`.arch-canvas/` 不存在）：别自己建目录、别写 `.mmd`，
先问用户，再用 `arch_switch { create: true }` 建一张（见下面「图的引用名」一节）。

## 先记住三件事

1. **这张图表达的是「讨论中的逻辑框架」，不保证与代码一致。**
   不要拿代码去纠正它，也不要因为图上没有某个模块就断定它漏了。
   它是讨论的画布，不是代码的镜像 —— 用户可能故意只画了一条链路。
2. **当前那张图每一步都已经在你的上下文里了。** 不要凭记忆回答图相关内容；
   只有当上下文里那份可能过期、或要看**别的**图时，才调 `arch_read`。
3. **用户在图上动一下，下一步你就能看见。** 反过来，你改完图，用户画布会同步，
   而且**你改动过的节点会短暂高亮** —— 所以说明里点名节点 id 很有用。

## 四个工具怎么选

| 场景 | 用哪个 |
|---|---|
| 看当前图 | 上下文里就有；不确定时才 `arch_read` |
| 改局部（加一个节点、改个标签、连一条线、挪个位置） | **`arch_edit`** —— 默认选择 |
| 画初稿 / 结构性重画 | `arch_write`（会继承同 id 节点的旧坐标与代码锚点，留言也按节点 id 保留在旁路表中，但仍会散掉未被重声明节点的布局） |
| 用户正看着 A，你想看一眼 B | `arch_read` 带 `diagram` —— **只读不切**，不会动用户的画面 |
| 确实要和用户一起看另一张 | `arch_switch` —— 用户的画布会跟着切过去 |

**默认永远先想 `arch_edit`。** `arch_write` 存在的唯一理由是初稿和结构性重画；
用它去改一处细节，用户手动摆好的布局就散了 —— 这是这个工具最容易被用坏的地方。

`arch_edit` 一次可以传多个 op，按顺序执行；遇到问题不会静默失败，会在 `problems` 里说明原因
（比如「节点 x 已存在，改用 set_label」）。**先看 `problems` 再向用户汇报。**

### op 一览

AI 用的 15 个：

`add_node` · `set_label` · `set_shape` · `set_link` · `move_node` · `remove_node` ·
`add_edge` · `remove_edge` · `set_edge_label` · `add_group` · `set_group` · `remove_group` ·
`set_direction` · `set_files`（给节点标源码文件）· `set_summary`（整张图的一句话总结）

界面用的 1 个：`mark_note`（把某节点的留言标成已办 / 重新打开）。**AI 不要调它** ——
留言读到就算送达，状态由这件事本身决定（见下文「用户留言」）。

形状：`rect` 矩形 / `round` 圆角 / `stadium` 胶囊 / `circle` 圆 / `diamond` 判定 /
`cyl` 数据库 / `hex` 六边形 / `sub` 子流程 / `asym` 旗形。

## 节点写什么：标题 · 意图 · 原理 · 引用

一个节点 = **标题**（它是什么）+ **描述**（为什么、要达成什么）+ **引用**（落在哪段源码）。
`label` 里用换行分段，**第一段是标题**，其余段是描述：

```jsonc
{ "op": "set_label", "id": "canvas",
  "label": "所见即所得的画布\n意图：不写代码也能把结构直接摆出来\n原理：文本是唯一真相源，图形只是它的一种视图" }
```

- **`意图：` 开头**的那段 = 这个元素想达成什么（对着人和 AI 说话，不写实现）；
- **`原理：` 开头**的那段 = 为什么这么设计、受什么约束（一句话说清依据）；
- 其他段当普通描述，照常显示。
- **技术名一律不写进 `label`** —— 文件名、类名、函数名走 `set_files`（`%% @file`）。
  节点上会自动多出一行 `▤ 文件名`，完整路径与校验状态在底部检查器里。

这是**惯例，不是框架硬约束**：解析器不认识 `意图：` / `原理：`，写了才分层着色，没写就当普通描述。
所以老图不必一次性改写，逐步迁移即可 —— 但**新加或改动的节点请按这个形状写**：
意图才是人和 AI 都读得懂的那一层，技术名换个人、换个仓库就失效了。

```jsonc
{ "ops": [
  { "op": "add_node", "id": "cache", "label": "缓存层", "shape": "cyl" },
  { "op": "add_edge", "from": "api", "to": "cache", "label": "命中查询", "arrow": "-.->" },
  { "op": "set_label", "id": "api", "label": "接入层（含鉴权）" },
  { "op": "set_files", "id": "api", "files": ["src/api/router.ts", "src/api/auth.ts#verify"] },
  { "op": "set_summary", "label": "接入层的鉴权与限流链路（讨论稿）" }
] }
```

## 图的引用名（key）

图库**跟着项目走**：每个项目目录下一个 `.arch-canvas/`，每张图一个 `.mmd` 文件。
引用一张图用**相对项目根的 key**：

| key | 含义 |
|---|---|
| `主流程` | 根图库里的 `主流程.mmd` |
| `支付/对账` | 子项目 `支付` 的图库里的 `对账.mmd` |

`arch_switch` 的 `key`、`arch_read` 的 `diagram`、`set_link` 的 `link` 都用这个写法。
`arch_switch` 遇到不存在的 key 会**列出可选图名** —— 照着它说的写就行，别猜。

**图库不会自动创建。** 项目里没有 `.arch-canvas/` 时：

- 不要自己建目录、不要写 `.mmd` 文件、也不要试 `arch_write`（会被拒，返回里会说明）；
- 用户**明确说了**要一张图（「画一张」「建个框架图」）之后，才用 `arch_switch { create: true }` 建；
  用户没提就先问一句，或者把结构写在回复里。

## 文件里那些 `%%` 行与留言：元数据照原样留，用户留的话必须回应

图文件里除了图体，还有四类 `%%` 行（`@summary` / `@pos` / `@link` / `@file`）与一类格式说明；用户的留言则存旁路表（`notes.json`），不写在源文本里：

```mermaid
%% @summary "接入层的鉴权与限流链路"       ← 整张图的一句话总结（图级，不挂节点）
%% @pos n1 120 40                          ← 画布坐标（用户拖出来的，数字不加引号）
%% @link n1 "支付/对账"                     ← 这个节点下钻到另一张图
%% @file n1 "src/api/router.ts#verify"     ← 这个节点对应哪段源码（可多条）
%%! @pos <节点id> <x> <y> …                ← 格式说明（`%%!` 开头，一律忽略）
```

**值一律带引号**：`%% @summary` / `%% @link` / `%% @file` 写出去时都给值加引号 ——
路径里有空格时按这个形状写才解析得对；只有 `%% @pos` 的两个数字不加引号。

- `@pos` / `@link`：**原样保留**，不要删、不要改、不要在回复里讨论它们。
  删掉 `@pos` 只是让节点重新自动布局；删掉 `@link` 就是解掉一次下钻。
  `@link` 是「一个节点展开成一张图」的写法，比给图分层级更贴合讨论时的放大/缩小。
  用户说「这个能展开讲讲」时，可以考虑给他建一张新图并 `set_link` 连过去。
- `@summary`：整张图的一句话总结，作用与 skill 的描述行一样 ——
  它会在你的上下文里以「**这张图讲的是**」单列一行，同一图库里别的图的总结也会顺带告知。
  **改图改了主题就顺手用 `set_summary` 更新它**；整体重画时你没写 `%% @summary`，
  宿主会沿用旧的那句（所以重画后记得看一眼它还对不对）。
- **用户留言（存 `notes.json` 旁路表）—— 一次性投递，不是待办**：
  用户在节点上留的一句话。它走独立表存储，不在 `.mmd` 源文本中：
  - **你会拿到注入给你的待递清单**（列出节点 id、标题与留言正文）—— **逐条回应，点名节点 id，不要当噪音略过**；
  - **读到就算送达**：宿主在这一步之后就把这一批从你的上下文里移除（历史只留最近 6 条）。
    所以**本轮一次处理完** —— 做不到的当场说清楚，别指望下一轮还看得到它。
    你**不需要、也不要**去 `mark_note` 标它：状态由「送达」这件事本身决定，没有任何人要维护它。
  - 已经投递过的不进你的上下文（上下文仅提示「另有 N 条已经投递过」），不要据此行动；要回看用 `arch_read`；
  - 留言的**正文**只能由用户写。留言不在源文本里，别去源文本改它。
  - 你整体重画（`arch_write`）或删除节点时，留言按节点 id 保留在旁路表中，不需要「继承」步骤，也不会因重画丢失。
  - **要长期挂着的意图不要放留言**（投递一次就没了）—— 那是节点描述或图内容的活，直接告诉用户。
- `@file`：**用户给节点标的源码文件**（「这个方块对应哪个文件」）。
  它们（连同校验结果）会在你的上下文里单列成「图元素上标的代码锚点」：
  带 ⚠ 的**已经失效，不要照着用** —— 重新定位后告诉用户锚点该改成什么，
  或者用 `set_files` 直接改（`路径` 或 `路径#符号`；传空数组清掉）。
  它只是**部分**节点的指路牌，不代表图与代码一致。
- **`drift`（图的保鲜状态）**：上下文里可能出现一段「图的保鲜状态」，那是宿主拿**内容指纹**
  比出来的（图上次写进文件时的代码 vs 现在），不是猜测。两种条目，处置完全不同：
  - 「这些锚点的文件改过了」= 锚点还指得到，但那段代码已经不是图上说的那个东西了。
    **别照着这些锚点去读**；要么重新定位，要么**先问用户这张图还准不准**（可能是图该改了）。
  - 「这些目录里有源码、却没有任何锚点指向」= 只是**还没画**，不是图上写错了。
    不要因此去重画一张没坏的图，也不要自己批量加锚点 —— 提一句给用户就行。
  没有这一段 = 没发现问题（干净时它不出现，别在回复里替它说话）。
- 锚点挂在**节点**上；节点删掉，锚点跟着消失。整体重画（`arch_write`）时锚点与一句话总结按节点 id 继承。
- `%%!` 开头的是**格式说明**（文件头部那几行），不是数据也不是给你看的任务，忽略即可。

## 反面清单

- ❌ 未经要求就把整张图重画（`arch_write` 只在初稿和结构性重画时用）
- ❌ **项目里还没有图库就自己建**（建目录 / 写 `.mmd`）—— 先问用户，再用 `arch_switch { create: true }`
- ❌ 拿代码去「纠正」图上的表达（图上没画 ≠ 漏了）
- ❌ 用 `arch_write` 改一处细节，把用户摆好的布局冲掉
- ❌ 凭记忆描述图的内容（上下文里就有当前版本）
- ❌ 在回复里复述 `@pos` / `@link` 等元数据行（但对**留言**相反：必须逐条回应）
- ❌ 把用户留言当噪音略过 —— 它们是**一次投递**：这一轮不处理，下一轮就没了
- ❌ 照着带 ⚠ 的 `@file` 锚点去读文件（那条锚点已经烂了）
- ❌ 用户看着 A，你 `arch_switch` 到 B 却没说要换（他会莫名其妙）
- ❌ 图是空的就大段猜，先看一眼再动手
